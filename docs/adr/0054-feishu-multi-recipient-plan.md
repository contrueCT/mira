# ADR 0054：飞书插件多接收人发送与精简入站消息

状态：Accepted，2026-11-14；已实现并通过本地验证，未部署。用户在方案之后明确批准开发，并要求默认支持多人私聊、取消本人配对限制。源码起点：`f316f44`。

## 目标与范围

直接扩展 `packages/feishu-channel`，沿用官方 Node SDK、Cordis、通用凭据和 Event/Wake。Mira 通过同一个飞书应用，按姓名找到人、按用户 ID 主动发消息，并引用收到的消息回复。发给其他人不要求对方先发消息或与插件配对。

入站给 Mira 提供正文、发送者姓名、可用用户 ID 和 `message_id`；其余信息按实际回复需要提供。姓名用于识别人，ID 用于执行，二者都保留。应用身份、租户和安装信息由插件处理。

默认接收应用收到的所有人类私聊消息，取消配对动作与本人入站筛选。来源始终为外部扩展；平台识别的发送者、姓名和已发送关系均不赋予其主人权限。保留一个持续 Mira，不按人创建独立 Life。群聊、媒体和用户身份代发不在本轮范围。

## 当前实现与需要改变的部分

| 当前行为 | 计划 |
| --- | --- |
| `feishu_send_message` 只收正文和可选引用 ID，发送到绑定的本人私聊 | 增加显式姓名、用户 ID 目标；要求明确目标或引用消息 |
| 引用只检查最近 512 条本人消息 ID（旧行为） | 持久保留每条已接收消息的精简引用记录，关联发送者、会话和应用连接 |
| 入站 payload 含来源信息和原文，缺少姓名 | 获取并冻结姓名；减少重复的业务字段 |
| 只要求私聊读取与机器人发送权限 | 通讯录能力单独检查和配置，基础收发继续可用 |
| 发送前记录 intent，结果未知不重放 | 保留，并把接收目标纳入不可变调用身份 |

依据：[插件 README](../../packages/feishu-channel/README.md)、[channel.ts](../../packages/feishu-channel/src/channel.ts)、[sdk.ts](../../packages/feishu-channel/src/sdk.ts)、[ADR 0036](0036-feishu-owner-channel.md)。

## 工具如何让 Mira 容易使用

保留 `feishu_send_message`，增加一个只读 `feishu_search_users`。日常按姓名发送只需要一次工具调用；遇到重名或只有姓名片段时，再使用搜索结果或向用户澄清。

发送参数：

```json
{"text":"明天下午三点开会。","recipientName":"张三"}
```

```json
{"text":"明天下午三点开会。","recipientId":"ou_example","recipientIdType":"open_id"}
```

```json
{"text":"收到，我来处理。","replyToMessageId":"om_example"}
```

| 参数 | 约定 |
| --- | --- |
| `text` | 必填；沿用文字长度限制与分段 |
| `recipientName` | 姓名查找；与 `recipientId` 二选一 |
| `recipientId` | 明确的用户 ID，允许发给未配对的人 |
| `recipientIdType` | 默认 `open_id`；明确支持 `user_id`，不靠字符串形状猜测 |
| `replyToMessageId` | 单独使用时从引用记录定位原会话；与目标同时使用时必须指向同一人 |

没有目标、也没有引用时返回 not_sent，要求指定接收人或引用 ID；不隐式选取最近对话。有明确目标时，已连接的应用即可发送，无需配对。

### 姓名解析规则

1. 只在当前应用可访问的通讯录范围查找。按用户 ID 去重，同一个人属于多个部门只算一次。
2. 搜索范围完整，且只有一个规范化后姓名完全匹配的人时，可以直接发送。只做去首尾空白和一致的 Unicode 规范化，不用拼音、昵称猜测或相似度自动选人。
3. 重名、只有模糊匹配或查询不完整时不发送，返回 `ambiguous_recipient` / `incomplete_search` 和少量候选。Mira 可以结合已有明确上下文选择 ID，或自然询问用户。
4. 搜索工具返回姓名、`open_id`；确有消歧需要且已获授权时附部门。使用 offset/nextOffset 返回每页最多 20 个候选；每次重新查询，不持久保存全量通讯录。不同页跨查询时结果可能变化，不能用单页判断唯一。分页返回少量候选，不把整份通讯录交给模型。
5. 缺权限、超时和无人匹配分别返回明确结果。局部结果不能冒充全范围唯一。

这是目标解析与数据完整性校验。是否发送、何时澄清仍由 Mira 依据用户意图决定，遵循 [ADR 0007](0007-model-owned-action-decisions.md)。

## 飞书接口与权限

所有发送保持应用身份，复用现有凭据，不引入 lark-cli、MCP 或用户 OAuth。

常见的 `/open-apis/search/v1/user` 关键词搜索接口要求用户身份；官方远程 MCP 的 `search-user` 也标注相同限制。因此，不能把它当成应用身份搜索的现成方案。[官方 MCP 工具说明](https://open.feishu.cn/document/mcp_open_tools/supported-tools?lang=zh-CN)

建议通过应用可见通讯录构建本次查询的候选集：

```text
应用通讯录授权范围（分页）
  ├─ 直接授权用户 → 获取用户信息
  ├─ 授权部门 → 子部门与直属成员（分页）
  └─ 授权用户组 → 核实成员展开接口及权限
                         │
                         ▼
                 按用户 ID 去重、匹配姓名
```

使用当前固定官方 SDK 已提供的 `contact.v3.scope.list`、`contact.v3.department.children`、`contact.v3.user.findByDepartment`、`contact.v3.user.get/batch`，实现前核实用户组展开方式。不得默认根部门 `0` 总是可读，不能要求所有应用都授权全公司通讯录。用户组或其他授权分支无法展开时，结果标记不完整，禁止按姓名自动发送。

按需分页查询，单次限制 100 个 HTTP 请求、5000 个不同用户、500 个部门、20 秒；预算耗尽返回不完整。不建立持久通讯录缓存。姓名自动发送必须完成本次范围查询；最终接收人一旦确定，在分段发送和调用恢复中保持不变。

权限分层：

| 能力 | 权限及配置方向 |
| --- | --- |
| 现有收发 | 保留 `im:message.p2p_msg:readonly`、`im:message:send_as_bot` |
| 按 ID 发送 | 不把通讯录查询权限变成发送的额外前置条件；由发送 API 校验可达性和所需字段权限 |
| 获取姓名 | 核对用户信息接口访问权限与 `contact:user.base:readonly` 姓名字段权限 |
| 按姓名查找 | 核对授权范围、部门与成员查询所需的最小权限组合和通讯录数据范围 |
| 租户内 `user_id` | 单独核对 `contact:user.employee_id:readonly` 的适用要求，缺少时明确提示 |

已用一个用户授权的真实应用验证：直接 search/v1/user 拒绝应用令牌；scopes 接口返回缺少通讯录范围权限，但根部门成员与全部可见子部门成员接口可读。按 ID 发送成功，用户确认收到测试消息。这证明根部门遍历可作为独立权限检查的回退路径，不证明所有应用都有根部门访问权。未增加或申请新权限，不记录真实人员 ID、密钥或令牌。实现时以对应接口当前要求核定最小集合；已有安装缺少新增权限时，在既有扩展设置说明缺少的能力，继续允许基础收发。新增授权及通讯录范围由用户或管理员明确配置，不自动扩大权限。

通讯录可见与消息可达分开判断：查到人不代表一定能主动发消息，发送仍受应用可用范围、租户策略和平台规则约束。[官方通讯录范围说明](https://open.larksuite.com/document/uAjLw4CM/ukTMukTMukTM/reference/contact-v3)、[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)

## 入站消息给 Mira 的内容

业务字段示意：

```json
{
  "senderName": "张三",
  "senderOpenId": "ou_example",
  "messageId": "om_example",
  "text": "请把进度发给李四。"
}
```

这里的 `messageId` 就是飞书 `message_id`，可直接传给 `replyToMessageId`。涉及原消息引用时才附相应引用 ID。默认不重复附应用 ID、租户、安装身份、会话类型和原始时间；通用事件外层已经保存来源与时间。`chat_id` 由插件引用记录解析，模型无需为普通私聊回复再携带一份。

Web 显示继续使用原正文及通用来源标签，不把内部路由信息塞进聊天正文。ContextProvider 只提供简短连接/能力说明，不逐轮重复联系人、完整身份及长篇使用说明。

当前 `renderWakeBatch` 会完整序列化扩展 payload，并保留通用来源和 History ID。因此本次通过精简插件 payload 与 ContextProvider 减少信息，保留通用外层结构；不会宣称模型最终只看到上述四个字段。实现时检查真正提交给 runtime 的输入，避免在正文、payload 和额外观察中重复注入姓名及说明，不为飞书增加核心专用渲染分支。

### 姓名解析与接收可靠性

长连接回调先持久写入私有收件箱并确认接收。姓名查询与后续 Host 投递由插件可恢复的消费者完成，不让网络查姓名拖住飞书 ACK；模型执行始终独立于 ACK。[官方长连接时限说明](https://open.feishu.cn/document/ukTMukTMukTM/uYDNxYjL2QTM24iN0EjN/event-subscription-configure-)

姓名按发送者 ID 读取官方用户信息，使用 1.5 秒有界等待，覆盖 SDK 取令牌和读取联系人阶段。只读 HTTP 同时传递取消信号，晚到结果不发布；同一连接的凭据对象复用官方 token cache。缺权限或网络不可用时仍保存并投递消息，姓名明确标为“姓名暂不可用”，保留 `senderOpenId` 供识别，不编造姓名。正常权限与网络条件下必须带真实姓名；异常降级可见且不丢消息。

首次发布前将姓名及事件内容一起冻结到收件箱。重复消息、重启和 Host 重试复用相同事件身份及相同内容，不能因姓名更新而产生不可变事件冲突。完整路由和来源证据在插件私有记录中保留；不改写已提交 History。改为“落盘即 ACK”必须覆盖 Host 投递失败后的恢复与状态提示，不能只启动一个易丢失的后台 Promise。

## 多接收人与发送记录

```text
目标解析 → 冻结目标与内容 → 持久 intent → 单次发送
                                      ├─ 确认成功 → 保存 message_id → 发布显示事件
                                      └─ 结果未知 → 保留证据，不自动重发
```

私有 SQLite schema 3 增加按消息 ID 索引的 incoming 表，与现有主行和发送 receipt 共用安装级 CAS；收件落盘后独立消费者解析姓名并投递。确认 Host 接收后压缩正文，保留来源摘要和引用身份；旧 pending inbox 保持原格式恢复。扩展现有发送 receipt，保存最终目标 ID/类型、应用连接、引用目标、内容摘要、分段 UUID 与实际返回会话 ID（写入已确认发送事件）。同一 call ID 查询已有记录时直接返回原结果，不能重新搜索姓名后改投另一人。历史 receipt 的身份和未知证据保持有效，必要的结构变化使用现有事务更新方式。

引用记录包含 `messageId → 发送者/会话/应用连接`，按消息分行持久保留，每条受现有 2 MB 限制，全库随消息数增长。引用记录缺失、过期或与指定接收人不符时明确不发送，不静默改成新消息。`user_id` 与 `open_id` 必须先在同一应用内解析为可比较的身份，不能直接比较两种字符串。

保留分段顺序、部分成功、取消、重连/解绑排空及 unknown 不重放。回执与已发送事件记录实际接收人，避免把发给其他人的消息标成发给本人。未发生发送的参数错误、搜索歧义和平台明确拒绝，与请求后断网等未知结果分别报告。

## 实施顺序与验证

1. 核定最小通讯录权限、应用身份可用接口和 ID 类型；完成 SDK 只读查询适配。先用合成 HTTP 验证分页、权限错误及查询预算。
2. 扩展搜索与发送工具，验证唯一姓名直发、重名澄清、按 ID 发送和引用目标一致性；接收人先解析冻结，再进入已有发送台账。
3. 扩展收件箱消费者与姓名冻结，精简入站 payload/ContextProvider；验证 ACK 时机、投递失败恢复和最终模型输入。
4. 更新插件 README、局部/根 AGENTS 与 ADR 0036 的范围说明；取消配对动作、保留历史控制消息已消费身份，遵循普通扩展及核心边界。
5. 每轮实现/修复按仓库要求使用全新、无实现对话的 `gpt-6.1-sol` / `max` 独立审查，修正后再审查。

主要回归：重复姓名跨页/跨部门、查询未完成、缺权限、姓名变化后重启、ID 类型与跨应用 ID、不同发言者的身份、出站接收人与入站会话隔离、引用错人、同 call ID 换目标、部分发送/未知结果/取消/重连，以及 Unicode 原文与历史读取。

使用现有 `feishu-sdk`、`feishu-channel`、`feishu-dialogue`、`feishu-store` 和 `recovery/feishu-inbound` 测试入口补充用例，运行适用的类型/包边界/离线检查；PostgreSQL 验证使用显式隔离测试库。当前实现的验证结果单列，不能把历史通过记录算作本次通过。

真实验收单列：用户授权后，用指定应用和明确的测试接收人验证不同发送者姓名/消息 ID、按姓名发送、按 ID 发送、引用回复及断线重启。合成测试不能证明真实权限或收发联通。

## 当前交付与验证边界

实现只修改源码、测试和文档，不修改运行中实例、模型配置或真实应用授权。新增通讯录授权及范围仍由管理员配置。真实 HTTP 查找/发送与用户收到消息已验证；修改后的插件 WebSocket、姓名补全和多人回复仍需在部署后单列真实验收。实现自测使用假 provider 与合成飞书传输。


### 当前验证记录（2026-11-14）

- 飞书专项离线测试：85/85，无跳过；含 SDK token 获取卡住时的取消、schema 1/2→3、跨进程 CAS、FIFO、姓名歧义和发送目标冻结。
- 五份 TypeScript 配置检查通过；包边界与 diff 格式检查通过。最终完整 `pnpm check` 通过：后端/基础 1396 项、Web 98 项，0 失败、0 跳过，包含类型、包边界和构建。
- 真实隔离 PostgreSQL 恢复：1/1，通过；覆盖 Host/Event/Wake/History、原文编码与重复输入。
- 浏览器门禁：1/1，通过；本机 Edge + 真实 HTTP/PG/runtime，合成模型与飞书传输，验证两人姓名/消息 ID 入模、各自引用回复、重启不重复。
- 全新独立审查已修正旧消息身份、入站 FIFO、HTTP 拒绝分类及取令牌时限问题；最终复审未发现阻塞缺陷。
- 未将修改部署到运行实例，未给实际应用增加权限；修改后的真实租户 WebSocket 联通仍未验收。
